01 / 从问题开始

响应丢失后，客户端知道什么？

客户端发起一次累加 10 的请求，服务端已经执行，响应却没有到达。此时再次发送请求，可能使累计金额从 10 变成 20。[1]

这里有两个独立事件：业务动作已经完成，客户端得到了结果。响应丢失只能说明第二个事件没有被客户端确认。客户端仅凭超时无法判断服务端是否完成了动作，因此重试需要考虑重复执行的影响。

我们用一个内存中的累计金额示例研究这个问题。累计金额从 0 开始，每次新请求增加 10。示例只处理串行调用，记录不会过期，执行过程中也不模拟进程崩溃。

每次调用都执行

执行两次相同的累加，累计金额依次为 10、20。程序只看金额，无法识别第二次调用的意图。

按请求标识识别

两次调用都携带 A。首次执行后保存记录，再次收到 A 时检查参数并返回原结果，累计金额保持 10。

02 / 解释机制

请求身份、状态与历史结果

服务端保存“请求标识、原始金额、返回结果”的对应记录。新的标识触发累加；已有标识先核对金额，再返回该标识原先保存的结果。金额相同的两次独立操作使用不同标识。[2]

在请求标识和参数固定时，重复执行应保持业务状态。这可以用一个状态变换表达：

  • S：服务端状态，包含累计金额和已处理请求记录。
  • k：固定的请求标识，本式同时假设请求金额相同。
  • ：处理该请求对状态产生的变换。

左侧处理同一请求两次，右侧处理一次，最终状态相等。这个性质约束业务效果；实际调用仍然可以发生多次。示例另外保存并重放历史结果，使客户端能够获得首次执行时的返回值。

区分两种数值

当前累计金额属于现在的系统状态，返回结果属于某次请求的执行记录。其他请求发生后，两者可能不同。重试 A 应返回 A 的原结果。

03 / 从流程到实现

把每一步对应到代码

字典保存请求记录。命中记录时，代码检查金额并立即返回；未命中时，代码才修改累计金额、生成结果并保存对应关系。下面是完整实现，retry.py 还包含可直接运行的演示与行为检查。

示例 1 / Python，保存请求参数与不可变结果
from dataclasses import dataclass

@dataclass(frozen=True)
class Receipt:
    total: int

class Ledger:
    def __init__(self):
        self.total = 0
        self.results = {}

    def charge(self, request_id: str, amount: int) -> Receipt:
        if request_id in self.results:
            original_amount, receipt = self.results[request_id]
            if original_amount != amount:
                raise ValueError("request_id 已用于其他金额")
            return receipt
        self.total += amount
        receipt = Receipt(total=self.total)
        self.results[request_id] = (amount, receipt)
        return receipt

首次收到 A 时，字典中没有 A，累计金额变成 10，并保存金额与结果。第二次收到 A 时，代码在修改累计金额之前返回，因此没有重复累加。首次收到 B 时没有命中旧记录，累计金额变成 20。

04 / 实践与解释

改变条件后，你能定位修改吗？

练习 1 / 预测与解释

相同金额，是否就是相同操作？

从空 Ledger 开始，依次调用 A，10；B，10；A，10。先写出每次返回值和最终累计金额，再运行验证。解释为什么第二次调用需要执行。

查看参考解

返回值依次为 10、20、10，最终累计金额为 20。A 与 B 表达两次独立操作，金额相同不足以判断它们是重试。第三次调用命中 A 的记录，因此返回首次结果 10。

如果只以金额作为字典键，B 会被错误地识别为 A 的重试。这个修改破坏了“独立操作独立执行”的要求。

练习 2 / 局部修改

增加收款人后，哪部分记录要变化？

给 charge 增加 recipient 参数。同一标识的金额与收款人都相同时重放结果，任一项变化时拒绝。保留串行、内存记录的条件，写出修改位置与三项检查。

查看参考解

把请求参数保存为金额和收款人的二元组，命中记录时比较整个二元组。金额更新和历史结果的生成位置保持在未命中分支。

参考修改 / 参数一致性
parameters = (amount, recipient)
if request_id in self.results:
    original_parameters, receipt = self.results[request_id]
    if original_parameters != parameters:
        raise ValueError("request_id 已用于其他参数")
    return receipt
# 未命中时执行原有累加，再保存：
self.results[request_id] = (parameters, receipt)

检查同标识同参数不会重复累加；同标识改收款人会拒绝且金额保持；不同标识同参数仍执行。只测试金额变化会遗漏新增条件。

练习 3 / 迁移与设计追问

把机制用于发送通知

某个流程会因超时重复发起同一通知。说明请求标识由谁生成、重试是否复用标识、服务端保存什么。再解释为什么当前内存示例还不足以覆盖“通知发出后进程退出”的情况。

查看参考解

在一次通知意图建立时生成标识，该意图的重试复用它。保存标识、接收方与内容等参数以及发送结果，防止同一标识被用于不同通知。

通知发出后、记录写入前退出，会使外部动作已经发生但本地记录缺失。当前字典模型不能保证这两步一起完成。实际方案需要结合通知服务的去重能力与持久记录设计，再验证具体失败路径；仅把字典换成数据库还不能证明问题已经解决。

05 / 总结与延伸

把理解落实到三个判断

面对重试，先判断哪些业务效果可能重复发生，再判断怎样识别同一次操作，最后确认记录与业务动作在什么条件下保持一致。三个判断分别影响副作用的位置、请求标识的生成方式和状态保存方式。

在当前模型中，你可以通过解释四步流程、运行代码、增加一个参数并验证结果来检查理解。迁移到真实系统时，再检查进程生命周期、并发与外部动作，按系统实际出现的条件扩展设计。
